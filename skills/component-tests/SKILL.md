# Стандарт: компонентные тесты — исполняемая спецификация

## Суть

Спецификация коробки описывается компонентными тестами — это и есть
автоматически проверяемая спецификация. Тест — не охота на баги и не погоня
за покрытием: он фиксирует, что коробка обещает на happy path и на отказе
каждого внешнего интегратора.

## Hard rules

1. **Чёрный ящик.** Тестируем через реальный интерфейс коробки (HTTP/CLI/очередь):
   запуск в Docker Compose, стабы внешних провайдеров — по их реальному протоколу,
   не моки в памяти.
2. **Формула.** `N = 1 (happy path) + Σ (различимые ветки адаптера i)` на срез.
   Один компонентный сценарий ⇔ один Extension юзкейса. Сценариев ровно N:
   пропущенный или выдуманный сценарий — ошибка проектирования.
3. **`@wip` до фиксации.** Все бизнес-сценарии держатся `@wip`; снятие `@wip` —
   акт фиксации результата (фиксером), не автора сценария. Минимум один `@smoke`.
4. **Границы — не компоненты.** Ветвление по полям `Request`, разбор формата,
   валидация диапазонов — юнит-тесты (см. `modules`). Компонент — только
   различимые ветки внешних адаптеров.
5. **Добавить/убрать/слить сценарий — акт дизайна**: сначала формула и юзкейс,
   потом `.feature`. Реализация воспроизводит спроектированное ровно.

## Существующий проект

Формула сверяется только если дизайн её объявил (`docs/design/**/contracts.md`).
Существующие сценарии без `@wip` — замечание (warn), не блок: приводи к
дисциплине при касании файла.

## Что проверяет скрипт

`check-component-tests` — все бизнес-сценарии `@wip`, есть `@smoke`, нет дублей
названий, число сценариев = N из дизайна (мягкий пропуск), рекурсивный поиск
`component-tests/**/*.feature`.

## STOP

- число сценариев не сходится с дизайном — добавить/убрать/слить сценарий может
  только проектировщик, не реализация;
- тест требует мока внешней системы вместо стаба по протоколу — стоп, это скрывает
  реальный отказ интегратора.

## Основание

Тест через реальный интерфейс ловит отказы сборки, которые моки в памяти
скрывают: стаб по реальному протоколу ведёт себя как внешняя система — включая
её отказы, — мок же проверяет наше представление о ней. Сценарии — исполняемая
спецификация (Gherkin ⇔ Extension юзкейсов), поэтому число сценариев
вычисляется формулой `N = 1 + Σ(ветки адаптеров)`, а не метрикой покрытия:
недостающий сценарий = дыра в дизайне, лишний = дублирование веток.
`@wip` до фиксации разделяет «написал» и «проверил»: снимает тег фиксер —
тот, кто видел зелёный прогон, а не автор. Место компонентных тестов в
пирамиде — середина: дороже юнитов, честнее к интеграции.
