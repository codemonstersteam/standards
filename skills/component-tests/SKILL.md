# Стандарт: компонентные тесты — исполняемая спецификация

## Смысл

Тест — исполняемая спецификация среза, не охота на баги и не погоня за
покрытием. Чёрный ящик: бинарник/сервис через реальный протокол, стабы —
по реальному протоколу провайдера, не моки в памяти.

## Где живут

`component-tests/features/*.feature` (Gherkin). Запуск — целиком в
Docker Compose, шаги — чёрный ящик (exit code, вывод, HTTP-ответы).

## Hard rules (проверяет `check-component-tests`)

1. Все бизнес-сценарии помечены `@wip`. Снятие `@wip` — акт фиксации
   результата, а не автора сценария.
2. Есть минимум один `@smoke`-сценарий (дымовой).
3. Нет дублей названий сценариев.
4. Число бизнес-сценариев равно формуле из дизайна
   `N = 1 + Σ(различимые ветки адаптеров)` в `docs/design/**/contracts.md`.
   Если формула не объявлена — сверка пропускается.

## Как работать

- Добавить/убрать/слить сценарии — это **акт дизайна**: сначала правка
  `contracts.md` с формулой, потом `.feature`. Реализация воспроизводит
  спроектированное ровно.
- Ветвление по полям `Request` — юнит-тесты, не компонентные сценарии.
- Получил `✗ …` от валидатора — исправь в том же ходу.
