# Стандарт: релиз — SemVer по совместимости + feature toggles

## SemVer: вес = совместимость

1. Единственная ось веса задачи — **совместимость задокументированного
   контракта** (SemVer 2.0.0 дословно): ломает контракт → `major`; добавляет
   способность → `minor`; иначе совместимое исправление → `patch`.
2. Багфикс, который сам ломает совместимость, — это **`major`**, не patch.
3. Только «сантехника» (lock-файлы, конфиги линтеров, CI-обвязка) — без тега.
   Всё неизвестное — продуктовое: лишний patch-тег дёшев, потерянная версия
   продуктового изменения — дорога.
4. Версия = git-тег на транке; VERSION-файлов нет — нечему разъезжаться.
   Тег ставится **только на влитый в транк** (после человеческого мержа),
   не на ветку.
5. Канаречный выпуск — пререлиз `X.Y.Z-canary.N`; канарейка не двигает базу
   версии.

## Feature toggles

1. **Вся новая способность едет за тогглом, default OFF.** Фича попадает в
   прод выключенной и открывается доле аудитории постепенно.
2. Тоггл зарегистрирован в системе управления тогглами; имя тоггла живёт в
   плане задачи.
3. **Включение — отдельный прогон оператора** (не входит в задачу-разработку):
   1% → 5% → 25% → 100% с наблюдением.
4. Тоггл — рычаг отката: RED-инцидент → тоггл OFF.
5. После 100% и стабилизации — тикет на удаление тоггла; мёртвые тогглы не копятся.
6. Ревьюер не принимает правки тестов/CI/логики тогглов, чтобы «позеленить» сборку.

## Существующий проект

Классифицируй по этим правилам новые изменения; ретроактивная тагировка истории
не требуется. Если релизный процесс команды другой — правила применяются к
новым версиям, договорённость о переходе фиксируется с оператором.

## Что проверяет скрипт

Ничего (guidance): детерминированный расчёт тега — уровень CI-рецепта, не
локальной петли. Проверяй осознанно при подготовке PR.

## STOP

- изменение ломает замороженный контракт (значит `major`) — сначала STOP
  и вопрос оператору, затем контракт по схеме `box-spec`;
- способность нельзя спрятать за тогглом (например, миграция схемы БД) —
  согласуй стратегию выпуска с оператором явно.

## Основание

SemVer (https://semver.org) кодирует совместимость контракта, а не объём
работы: потребитель читает версию как обещание, поэтому ось веса — один —
ломает/добавляет/чинит. Тогглы отделяют выпуск от деплоя (deploy ≠ release):
код в транке ещё не значит способность у пользователей — классика Фаулера
(https://martinfowler.com/articles/feature-toggles.html). Постепенное
включение 1% → 100% и тоггл как рычаг отката возвращают управляемость,
которую теряет непрерывный деплой; удаление отработавших тогглов — плата
за это удобство, иначе долг растёт.
