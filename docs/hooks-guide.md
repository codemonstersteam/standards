# Руководство по хукам

Как устроен моментный контроль dev-standards: контракт, качество,
производительность, антипаттерны. Живой эталон — [`hooks/standards-post-tool.mjs`](../hooks/standards-post-tool.mjs)
(75 строк) + [`lib/common.mjs`](../lib/common.mjs); этот документ разбирает его по решениям.

## Роль и где стоит

Хук — **advisory-контроль в моменте**: сразу после правки файла модель получает
`✗`-список нарушений и исправляет их в том же ходу. Он никогда не блокирует
инструмент; финальная гарантия — pre-commit-отчёт и CI ([иерархия контроля](combining-approaches.md)).

Постановка (`install.sh`):

| Харнес | Куда | Как исполняется |
|---|---|---|
| dsh | `.standards/hooks.json` (matcher `write\|edit`) | мост `@deepseek-ai/dsh-hooks-claude-code` из `~/.dsh/cordis.patch.yml` |
| ZCode | `~/.zcode/cli/config.json` (user-конфиг: проектные hooks игнорируются) | нативно, PostToolUse |
| Claude Code | проектный `.claude/settings.json` (matcher `Write\|Edit`) | нативно, коммитится в репо |

opencode и pi контроль в моменте делают иначе (плагин и extension), см. [«Каналы контроля»](#каналы-контроля-момента).

## Контракт ввода/вывода

**Вход** — JSON на stdin (`hooks/standards-post-tool.mjs:12-29`):

```json
{ "tool_name": "edit", "tool_input": { "file_path": "src/api/user.ts" }, "cwd": "/proj" }
```

Путь файла ищется по кандидатам `file_path ?? filePath ?? path ?? notebook_path`
(строка 27) — харнесы называют поле по-разному. Команда (`tool_input.command`)
используется для TBD-контроля на `git commit`.

**Выход** — всегда `exit 0`; либо пустой stdout (нарушений нет / файл вне зон
стандартов / любая внутренняя ошибка), либо JSON:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "[dev-standards] Нарушения стандартов:\n  [box-spec] ✗ ...\nИсправь нарушения в этом же ходу. Подробности правил: skills box-spec, ...".
  }
}
```

`additionalContext` дописывается в контекст модели. Каждая строка нарушения
снабжена id стандарта (`[box-spec]`), маркером `✗` (его же ищут чекеры в stderr)
и подсказкой, в каких скиллах читать правила — список собирается из манифеста,
не хардкодом (`standards-post-tool.mjs:59`).

## Алгоритм

1. Прочитать stdin, распарсить JSON (ошибка → тихий `exit 0`).
2. Резолвнуть путь от `cwd`, найти project root по предку с `.git`
   (`findProjectRoot`, `lib/common.mjs:41`); правка вне проекта — тихий выход.
3. Для каждого стандарта из `standards.json` — для каждого `checks[]`:
   если относительный путь матча `check.paths` (glob `*`, `**`, `?` —
   `pathMatches`, `lib/common.mjs:36`) — запустить чекер.
4. Запуск — отдельный процесс `node checks/<name>.mjs <projectRoot>`
   (`runCheck`, `lib/common.mjs:95`): из stderr собираются `✗`-строки.
5. Нет пути, но `tool_input.command` — `git commit` → `check-tbd` (ветка,
   дифф, коммит в trunk).
6. Нарушения есть → `additionalContext`; нет → тишина.

Фильтрация **по путям из манифеста, а не по имени тула**: правка любого
инструментом (`edit`, `write`, notebook) обрабатывается одинаково; новый чекер
или зона путей добавляется записью в `rule.yaml` без правки хука.

## Правила качества хука

1. **Одна ответственность.** Хук только фильтрует и запускает; вся логика
   проверок — в чекерах (`checks/*.mjs`) с их собственным контрактом и тестами.
   Хук не парсит OpenAPI и не ходит в git руками.
2. **Чёткий контракт ввода/вывода.** JSON на stdin → JSON в stdout, `exit 0`
   всегда. Формат события — Claude hooks API
   (https://docs.anthropic.com/en/docs/claude-code/hooks); мост dsh исполняет
   его же, поэтому хук один на три харнеса.
3. **Быстрое выполнение.** Замер на этом репозитории (Apple Silicon, Node 22):
   файл вне зон стандартов — ~0.12–0.19 с; файл с матчем (spawn двух чекеров:
   `check-api-spec` + `check-docs`) — ~0.14 с. Доминирует старт node-процесса,
   сами проверки дёшевы. Хук вызывается на каждый tool use, но advisory-ценность
   появляется уже на фоне хода модели (секунды) — вклад ~150 мс незаметен.
   Тяжёлые проверки (полные прогоны тестов, `spectral`, `oasdiff`) в хук не
   ставятся — им место в pre-commit/CI.
4. **Fail-open.** Три уровня: ошибка чтения stdin → `exit 0`; непарсимый
   JSON → `exit 0`; любое исключение в `main` → `catch` → `exit 0`
   (`standards-post-tool.mjs:75`). Стандарты не имеют права ронять харнес.
5. **Ясные сообщения.** Формат нарушения: `[<id стандарта>] ✗ <что случилось>`
   + общий хвост «Исправь … в этом же ходу. Подробности: skills …». Текст
   `✗`-строки — ответственность чекера: файл, суть, что сделать.

## Производительность

| Сценарий | Замер | Почему |
|---|---|---|
| Файл вне зон (`paths` не матчятся) | ~0.12–0.19 с | старт node + чтение `standards.json`; чекеры не запускаются |
| Файл в зоне, нарушений нет | ~0.14 с | + spawn 1–2 чекеров (фикстуры малы) |
| Файл в зоне, есть нарушения | ~0.14 с | то же + сбор `✗`-строк |

Кэширования нет — и при таких цифрах оно не нужно: хук живёт один вызов
(новый процесс на каждый tool use), межпроцессный кэш дал бы race-условия
и инвалидацию ради сэкономленных ~20 мс. Если будущие чекеры станут тяжёлыми,
правильный ход — не кэш в хуке, а перенос проверки в pre-commit/CI
(см. [combining-approaches](combining-approaches.md)).

## Антипаттерны

| Антипаттерн | Как у нас |
|---|---|
| Монолитный хук «на всё» (логика проверок внутри хука) | Хук — 75 строк диспетчеризации; логика в чекерах |
| Хук бросает исключение / ненулевой exit | `exit 0` всегда; ошибки — в `additionalContext`, либо тишина |
| Блокировка инструмента при нарушении | Advisory: модель видит список и правит; блокирует только opencode-канал (ниже), и то по его контракту |
| Хардкод списков правил/скиллов в хуке | Всё из `standards.json`; добавление стандарта = запись в `rules/` |
| Фильтрация по имени тула (`if tool_name === 'edit'`) | Фильтрация по путям манифеста — имя тула неважно |
| Тесты «на наличие файла хука» вместо поведения | `test/run.mjs` гоняет хук процессом с stdin-JSON и ассертит вывод (см. ниже) |
| Тяжёлая проверка в моменте (полные тесты) | В хуке только дешёвые статические чекеры; тяжёлое — pre-commit/CI |

## Каналы контроля момента

Один и тот же набор проверок доставляется тремя способами — различия только в
поверхности харнесов:

| | dsh / ZCode / Claude (hook) | opencode (плагин) | pi (extension) |
|---|---|---|---|
| Файл | `hooks/standards-post-tool.mjs` | `opencode-plugin/standards-guard.mjs` | `pi-extension/index.mjs` |
| Событие | PostToolUse (после тула) | `tool.execute.before` (до тула) | `tool_result` (после тула) |
| Нарушение | `additionalContext` в контекст модели (advisory) | `throw Error` — блокирует тул | патч контента результата |
| Особенность | мост dsh / user-конфиг ZCode | `write` проверяет будущее состояние (контент до записи на диск) | у pi нет hooks/MCP — потому патч |
| Отказ инфраструктуры | fail-open | fail-open | fail-open |

Общее правило канала: где харнес позволяет блокировать, это остаётся
осознанным исключением (opencode), а не нормой; ядро v0.5 — advisory.

## Тестирование хука

`test/run.mjs`, секция «2. Hook (Claude-формат) на эмуляции stdin»: хук
запускается процессом с `input:`-JSON, ассертится `status` и парсится stdout.

Покрыто: advisory-`exit 0`; структура `hookSpecificOutput.additionalContext`;
`✗` в тексте; динамический список скиллов; посторонний путь → пустой stdout;
good-фикстура → тишина; fail-open на битом/пустом stdin; бюджет времени.

Новый кейс = новый `run('node', [hook], { input: … })` + `ok(...)`: хук —
чёрный ящик, мокать нечего (вся файловая система — фикстуры `test/fixtures/`).
