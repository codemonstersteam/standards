## 3. Углублённое руководство по хукам: качество, производительность, паттерны

Этот раздел должен стать **сердцем** технической документации.

### 3.1. Качество кода хуков: как писать правильно

**Правила хорошего хука:**

1. **Один хук — одна ответственность**. Хук `standards-post-tool.mjs` должен только запускать проверки и формировать контекст. Не вставляйте в него логику чтения файлов, если это не нужно.

2. **Чёткий контракт ввода/вывода**. Хук получает параметры инструмента (например, `path` для `edit_file`) и возвращает строго определённый объект:

```json
{
  "additionalContext": "⚠️ Обнаружено нарушение стандарта API First:\nФайл src/api/user.ts изменен, но нет соответствующего обновления в openapi.yaml.\nЗапустите 'npm run api:sync' для синхронизации."
}
```

3. **Быстрое выполнение (<100ms)**. Хук вызывается после каждого использования инструмента. Долгие операции (например, полный запуск тестов) нужно выносить в pre-commit или CI.

4. **Устойчивость к ошибкам (fail-open)**. Если внутренняя проверка упала, хук должен вернуть пустой `additionalContext`, а не блокировать весь процесс Claude Code.

5. **Ясные сообщения об ошибках**. Используйте структурированный вывод с указанием:
   - Какого стандарта нарушено.
   - Где (файл, строка).
   - Как исправить (конкретная команда или шаг).

**Антипаттерны (как не надо):**
- Монолитный хук на 500 строк, который делает все сразу.
- Хук без логирования. Если что-то пошло не так, вы не узнаете почему.
- Хук, который блокирует выполнение (выбрасывает исключение). Это нарушает работу всего Claude Code.

### 3.2. Производительность хуков

**Факты:**
- Хук в Claude Code вызывается **синхронно** после каждого tool use. Время его выполнения **прямо добавляется к времени ответа** модели.
- Оптимальное время работы хука: **<50-100ms**. Для сравнения, запуск `node checks/run-all.mjs` может занять секунды.

**Рекомендации по оптимизации:**

1. **Используйте манифест `standards.json`** для фильтрации проверок по путям файлов. Не запускайте `check-api-spec` для файлов в `tests/`.

```javascript
// В хуке, на основе standards.json
const relevantChecks = checks.filter(check =>
  check.paths.some(path => filePath.startsWith(path))
);
```

2. **Кэшируйте результаты тяжёлых проверок**. Если `check-api-spec` уже запускался для этого файла недавно и файл не менялся, можно вернуть кэшированный результат.

3. **Выносите сложную логику в отдельный процесс**. Если проверка требует запуска внешнего инструмента (например, `spectral` для линтинга OpenAPI), делайте это асинхронно и кэшируйте результат.

### 3.3. Обязательное тестирование хуков: не только наличие, но и поведение

**Критически важное требование**: Тесты в `test/run.mjs` должны **не только проверять, что хук установлен**, но и **тестировать его логику**.

**Что должно тестироваться:**

```
Тестирование хука
├── 1. Установка (Проверка конфигов)
├── 2. Логика (Запуск с mock-параметрами)
│   ├── Возвращает ожидаемый additionalContext
│   ├── Фильтрует проверки по путям
│   └── Не превышает лимит времени
└── 3. Граничные случаи (Ошибки, пустые данные)
    ├── Не падает при отсутствии файла
    ├── Корректно обрабатывает JSON-ошибки
    └── Работает в 'strict' и 'report' режимах
```

**Пример теста для хука (должен быть добавлен в `test/run.mjs`):**

```javascript
// В test/run.mjs, новый блок
describe('Hook behavior', () => {
  test('standards-post-tool should return violations for modified API file', async () => {
    // Мокируем параметры tool call
    const mockToolCall = {
      tool: 'edit_file',
      params: { path: 'src/api/user.ts' },
      result: { success: true }
    };

    // Запускаем хук
    const result = await runHook('standards-post-tool.mjs', mockToolCall);

    // Проверяем, что он вернул контекст с нарушением
    assert(result.additionalContext.includes('API First'));
    assert(result.additionalContext.includes('openapi.yaml'));
  });

  test('standards-post-tool should not run check-api-spec for test files', async () => {
    const mockToolCall = {
      tool: 'edit_file',
      params: { path: 'tests/user.test.ts' } // Файл вне зоны API
    };

    const result = await runHook('standards-post-tool.mjs', mockToolCall);
    // Проверки API не должны были запускаться
    assert(!result.additionalContext.includes('API First'));
  });

  test('standards-post-tool should complete in under 100ms', async () => {
    const mockToolCall = {
      tool: 'edit_file',
      params: { path: 'src/utils.ts' }
    };

    const start = process.hrtime.bigint();
    await runHook('standards-post-tool.mjs', mockToolCall);
    const end = process.hrtime.bigint();

    const durationMs = Number(end - start) / 1e6;
    assert(durationMs < 100, `Hook took ${durationMs}ms, expected <100ms`);
  });
});
```

**Инструменты для тестирования:**
- Используйте **`node --test`** или **`vitest`** для запуска тестов.
- Мокируйте вызовы к файловой системе (`fs.promises.readFile`) и к внешним командам.
- Тестируйте хук как **чёрный ящик**, подавая на вход разные данные и проверяя вывод.

## 4. Рекомендации по комбинированию подходов: иерархия контроля

Этот раздел должен быть **визуальным и чётким**. Он отвечает на вопрос: "Где какой контроль применять?"

### 4.1. Иерархия контроля (пирамида)

```
        ╱╲
       ╱  ╲
      ╱ CI ╲          ← Абсолютная гарантия
     ╱──────╲
    ╱ Pre-   ╲        ← Высокая гарантия
   ╱  commit  ╲
  ╱────────────╲
 ╱   LLM-хук    ╲      ← Мгновенная обратная связь (advisory)
╱────────────────╲
```

**Описание уровней (добавить в `docs/combining-approaches.md`):**

| Уровень | Инструмент | Гарантия | Скорость | Лучше всего подходит для |
|:---|:---|:---|:---|:---|
| **Контроль в моменте** | LLM-хук (PostToolUse) | Низкая (advisory) | Мгновенная | **Обучение AI**, предупреждение, мягкие правила, проверка **модельных** стандартов (стиль, архитектурные решения). |
| **Pre-commit** | `pre-commit` | Высокая | Быстрая (сек) | **Личные** стандарты разработчика, быстрый тест, **скриптовые** проверки. |
| **CI/CD** | GitHub Actions / GitLab CI | **Абсолютная** | Задержка (мин) | **Обязательные** стандарты команды, сложные тесты, интеграционные проверки. |

### 4.2. Конкретные рекомендации по комбинированию (для 4 практик)

| Практика | Контроль в моменте (LLM-хук) | Pre-commit | CI/CD | Комментарий |
|:---|:---|:---|:---|:---|
| **API First** | Хук проверяет, **если изменился код в `src/api/`,** то **подсказать** обновить `openapi.yaml`. | Запуск `check-api-spec` для изменённых файлов. | Запуск `check-api-spec` + `spectral` для всех файлов в `src/api/`. | **CI — обязателен** для гарантии актуальности контракта. |
| **TBD (Trunk-Based)** | Хук может отслеживать количество коммитов в ветке и **предупреждать**, если она старая. | Лёгкий чек: `git log --oneline \| wc -l` ≤ 2 дня. | Полный `check-tbd` с проверкой diff и времени ветки. | **CI — единственный гарантийный механизм** против долгоживущих веток. |
| **Feature Toggles** | Хук может проверять, что при создании toggle-файла **есть ссылка на задачу** в комментарии. | Проверка формата toggle-файла. | Проверка наличия теста для toggle. | Основная проверка — **скриптовая** (`check-feature-toggles`). |
| **Component Tests** | Хук может **подсказывать** формулу `N = 1 + Σ` при создании нового компонента. | Запуск `check-component-tests` для изменённых файлов. | Запуск всех тестов компонента. | **CI — обязателен** для запуска всего набора тестов. |

**Общий принцип**: **Контроль в моменте — для обучения и мягких правил. Pre-commit — для быстрых, личных проверок. CI — для строгих, обязательных проверок.** Это **не конкуренция, а сотрудничество**.

## 5. Примеры реализации проверок для ключевых практик

**Чекер (`checks/check-tbd.mjs`):**

- Согласованность имён toggle-файлов и кода.
