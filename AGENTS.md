# Стандарт разработки (эталон dev-standards)

## Принципы

1. **API First. Контракт первичен и заморожен.** Изменение поведения — сначала в
   `api-specification/openapi.yaml` (маркер `x-frozen:`), затем в коде.
   Никогда наоборот. Breaking замороженного контракта — STOP, вопрос оператору.
2. **Дизайн раньше кода. Модуль = один вход, один выход.** Срез = 1 внешнее
   входящее воздействие = 1 Request; код среза живёт в `internal/<slug>/` и
   имеет ровно одну точку входа (index/handler/request/usecase) и один
   публичный результат — наружу ничего кроме него. Межмодульное — только через
   контракты. Дизайн среза — в `docs/design/slice-*/`: контракты и формула
   компонентных сценариев `N = 1 + Σ(различимые ветки адаптеров)`.
3. **Тесты — исполняемая спецификация**, не охота на баги и не погоня за
   покрытием. Компонентные тесты по формуле: чёрный ящик, стабы по реальному
   протоколу провайдера, запуск в Docker Compose; сценариев ровно N; все
   бизнес-сценарии `@wip` до фиксации; smoke обязателен.
4. **Trunk-Based Development.** Один `trunk`; feature-ветка ≤ 2 дней;
   один тикет = один PR ≤ 600 строк; ветки не ответвляются от веток;
   напрямую в trunk не коммитим.

## Петля разработки

требование → срез → контракт и дизайн (`docs/design/`) → тикеты (минимальные,
атомарные) → реализация по TBD → компонентные тесты (`@wip`) → фиксация
(снятие `@wip` — акт фиксации результата, не автора сценария) → документация.

## Что проверяется автоматически (детерминированно, до CI)

- `check-api-spec`: `api-specification/openapi.yaml` существует; `openapi: 3.x`;
  в `paths:` есть пути; описаны `responses:`; есть маркер `x-frozen:`.
- `check-component-tests`: `*.feature` в `component-tests/**`; все бизнес-сценарии
  `@wip`; есть `@smoke`; нет дублей названий; число бизнес-сценариев = N из
  `docs/design/**/contracts.md` (если формула не объявлена — сверка пропускается).
- `check-modules`: в каждом `internal/<slug>/` ровно одна точка входа
  (index/handler/request/usecase); `internal/shared/` — исключение.
- `check-tbd`: нет коммитов напрямую в trunk/main/master; дифф feature-ветки
  против trunk ≤ 600 строк; ветка живёт ≤ 2 дней.

Замечания валидатора (`✗ …`) возвращаются тебе сразу после правок — исправляй
в том же ходу. Контроль advisory: финальная гарантия — pre-commit/CI.

## Стоп-условия (STOP — остановись и спроси оператора)

- нужно сломать замороженный контракт или сменить/снять `x-frozen`;
- число сценариев не сходится с дизайном (добавить/убрать/слить сценарий —
  это акт дизайна, а не кодинга);
- задача меняет границы модулей или требует нового среза.

Подробности: skills `api-spec`, `component-tests`, `tbd`, `modules`
(поставляются вместе со стандартом).
