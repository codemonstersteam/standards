# Стандарт разработки (эталон dev-standards)

## Принципы

1. **Box-first. Контракт первичен.** Проектирование начинается со спецификации
   коробки (сервис/утилита/компонент — всё, что предоставляет API): контракт
   описан и заморожен (`x-frozen:`), документация выводится из контракта
   (`spec → docs → code`). Изменение поведения — сначала контракт, потом код.
   Breaking замороженного контракта — STOP, вопрос оператору.
2. **Тесты — исполняемая спецификация.** Спецификация коробки описывается
   компонентными тестами: чёрный ящик, стабы по реальному протоколу,
   Docker Compose; сценариев ровно `N = 1 + Σ(различимые ветки адаптеров)`;
   все бизнес-сценарии `@wip` до фиксации; smoke обязателен.
3. **Модули: 1 вход, 1 выход.** Модуль принимает одну сущность и возвращает
   один `Result<T, Error>`; вход валидируется по доменным диапазонам;
   valid-by-construction (приватное состояние + фабрика); ошибки — значения
   (ROP), маппятся на транспорт один раз на краю; чистое ядро, I/O — оболочка;
   вертикальные срезы вместо технических слоёв; data flow (head-pipe) рисуется
   для человека и машины — это помогает уточнить упущенные требования.
4. **TBD.** Один trunk; ветка ≤ 2 дней; тикет = PR ≤ 600 строк; напрямую в
   trunk не коммитим; мержит человек; CI красный — не пушим.
5. **Релиз.** Вес изменения = совместимость контракта (SemVer); новая
   способность едет за тогглом default OFF, включение — отдельный прогон;
   тоггл — рычаг отката.

## Существующий проект

Стандарт применяется к **новому и изменяемому** коду: легаси не требует
немедленной переделки — при касании файла приводи его к правилам. Проверки
прогрессивны: отсутствующие артефакты — мягкий пропуск, большинство нарушений —
замечания (warn), финальная гарантия — pre-commit-отчёт и CI.

## Что проверяется автоматически (детерминированно)

- `check-api-spec`: контракт существует; `openapi: 3.x`; `paths:`; `responses:`;
  маркер `x-frozen:`.
- `check-component-tests`: все бизнес-сценарии `@wip`; есть `@smoke`; нет дублей;
  число сценариев = N из `docs/design/**/contracts.md` (если не объявлена — пропуск).
- `check-modules`: в каждом `internal/<slug>/` ровно одна точка входа
  (index/handler/request/usecase); `internal/shared/` — исключение.
- `check-constructors` (Go, только изменённые файлы): доменные типы строятся
  фабрикой с проверкой, нет голых литералов вне фабрики.
- `check-docs`: при существующем контракте — README с pipe-блоком и таблицей отказов.
- `check-tbd`: нет коммитов в trunk/main/master; дифф ветки ≤ 600 строк; ветка ≤ 2 дней.

Замечания валидатора (`✗ …`) возвращаются сразу после правок — исправляй в том
же ходу. Контроль advisory: финальная гарантия — pre-commit-отчёт и CI.

## Стоп-условия (STOP — остановись и спроси оператора)

- нужно сломать замороженный контракт или сменить/снять `x-frozen`;
- число сценариев не сходится с дизайном (сценарий — акт дизайна, не кодинга);
- задача меняет границы модулей, требует нового среза или второго входа в модуль;
- доменный диапазон поля неизвестен — вернись к требованиям.
